# mkmoney MVP 설계

상태: 사용자가 자체 호스팅 방향, 화면 목업, 상세 설계 진행을 승인했다. 2026-11-06에 확정한 구현 기준 문서다.

## 의도와 배경

첫 사용자인 강민씨가 뱅크샐러드 엑셀로 가계부를 누적 관리하고, 잔액 추정 대신 월별·사용자 지정 기간별 수익과 지출, 카드 사용액, 분류별 현황을 확인하는 개인용 웹앱이다. 앱은 집 안의 개인 서버에서 실행하고 PostgreSQL에 거래를 보관한다. PC와 휴대폰은 같은 사설 네트워크에서 웹 브라우저로 사용한다.

## 성공 기준

- `expense-20xx-xx-xx.xlsx` 파일의 `가계부 내역` 시트를 브라우저에서 읽고 거래를 미리 볼 수 있다.
- 가져오기 검토와 사용자 승인 뒤 신규 거래만 FastAPI를 통해 PostgreSQL에 추가한다. 기존 거래는 가져오기로 자동 수정하거나 삭제하지 않는다.
- 같은 파일을 다시 가져오면 이미 반영된 행은 중복 추가되지 않고, 신규 행만 추가된다.
- 월별 및 직접 지정한 날짜 구간으로 수익·지출·차액, 원본 분류별 금액을 확인한다. 월 비교는 전체 전월 또는 전월의 같은 날짜 구간을 선택할 수 있다.
- 별도 화면에서 원본 결제수단별 실제 구매 사용액을 확인하고, 저장된 매핑을 통해 신용·체크·기타로 구분한다.
- 집 안 네트워크의 데스크톱과 모바일 브라우저에서 핵심 현황, 가져오기 검토, 승인을 사용할 수 있다.
- 실제 금융 거래 데이터는 집 밖 서비스로 보내지 않고, 앱 서버 로그와 개발 자료에 복사하지 않는다.

## 검토한 접근과 선택

1. **브라우저 전용 저장(IndexedDB)**: 거래가 앱 서버로 가지 않아 데이터 경계가 단순하지만, 사용자가 지정한 PostgreSQL/FastAPI를 충족하지 못하고 개인 서버에서 여러 기기로 공유 조회하기 어렵다. 제외한다.
2. **개인 장비 자체 호스팅(선택)**: Vite 웹앱과 FastAPI를 집 안 서버에서 제공하고, PostgreSQL에 거래를 저장한다. 엑셀 파일 자체는 브라우저에 남기며, 사용자가 승인한 정규화 신규 거래만 같은 집 안 서버로 전송한다. 사용자는 PC와 휴대폰에서 같은 DB를 볼 수 있고 금융 데이터가 외부 SaaS로 가지 않는다. 서버가 켜져 있어야 하고 사설 네트워크 설정·백업 책임이 있다.
3. **공개 또는 외부 클라우드 호스팅**: 어디서나 접속할 수 있지만 금융정보가 외부 서버에 저장되고 공개 배포·인증·보안 관리 범위가 커진다. 현재 단일 사용자·집 안 사용 목적에는 선택하지 않는다.

## 범위

### 이번 MVP

- 반응형 웹 대시보드, 거래내역, 엑셀 가져오기 검토, 카드 사용, 암호화 백업·복원.
- 뱅크샐러드 `.xlsx` 중 `가계부 내역` 시트 가져오기. 이 시트의 현재 헤더는 `날짜`, `시간`, `타입`, `대분류`, `소분류`, `내용`, `금액`, `화폐`, `결제수단`, `메모`다. 헤더명으로 열을 식별하고 열 위치에 의존하지 않는다.
- `뱅샐현황` 등 거래 시트가 아닌 시트는 거래 가져오기에서 제외하고 값은 읽거나 저장하지 않는다. 가져올 시트 이름을 승인 전에 분명히 보여준다.
- 날짜, 시간, 거래 유형, 금액, 통화, 결제수단, 내용 기준으로 중복을 찾아 새 거래만 추가한다.
- 원본 `타입`, `대분류`, `소분류`를 보존하며 수익·지출·이체·환불 구분 및 분류별 현황을 제공한다. 예: 식비, 보험, 저축, 임대수익, 카드 사용 관련 분류. 실제 원본 분류 문자열을 임의로 개명하거나 합치지 않는다.
- 월별·직접 지정 기간별 집계, 전체 전월 및 전월 동일 날짜 구간 비교.
- 신용·체크카드별 실제 구매 거래 사용액. 원본 결제수단 라벨이 카드 종류를 명확히 나타내지 않으면 사용자가 신용·체크·기타로 매핑하며, 설정은 다음 가져오기에도 유지한다.
- 사용자 암호로 암호화한 백업 파일 내보내기·복원. 복원은 기존 행을 덮어쓰거나 삭제하지 않고, 가져오기와 같은 중복 규칙으로 신규 행만 미리보기·승인 후 병합한다.
- 단일 사용자용으로 사설 네트워크 범위에서만 접근하는 운영 방식.

### 제외

- 공개 인터넷 서비스, 여러 사용자/가족 계정, 여러 서버 간 동기화.
- 금융 계좌 자동 연결·은행 API, 상품 검색·추천, 투자 판단, 예·적금·대출 시뮬레이션, 연금 분석.
- 서로 다른 통화 간 환전·환율 적용.
- 가져오기 기능으로 기존 거래를 정정·삭제하거나 원본 파일과 DB를 양방향 동기화.

## 가져오기 및 중복 정책

1. 브라우저에서 `.xlsx`의 시트 목록과 헤더를 읽어 `가계부 내역`을 선택한다. 원본 워크북 바이트는 API에 보내지 않는다.
2. 지원 형식, 필수 헤더, 날짜, 금액, 통화, 행별 누락·오류를 검증한다. 모호한 값은 추정해 반영하지 않고 검토 대상으로 표시한다.
3. 각 행을 기존 DB와 비교해 신규, 기존 중복, 파일 내부 중복, 검토 필요 상태로 나눈 미리보기를 보여준다. 날짜는 기간 범위와 거래일 표시에 쓰며, 날짜만으로 중복 처리하지 않는다.
4. 합의된 정확 중복 키는 정규화한 `날짜 + 시간 + 타입 + 금액 + 화폐 + 결제수단 + 내용` 조합이다. 날짜는 `YYYY-MM-DD`, 시간은 `HH:MM:SS`(없으면 빈 문자열), 금액은 부호를 보존한 정규 십진 문자열, 통화는 대문자, 텍스트는 Unicode NFC 정규화 후 앞뒤 공백 제거를 사용한다. 필드 배열을 구분자가 명확한 UTF-8 JSON으로 직렬화한 뒤 SHA-256 fingerprint를 만든다. `대분류`, `소분류`, `메모`는 키에서 제외한다. 동일 키가 DB에 있으면 자동으로 건너뛰고 기존 행을 수정하지 않는다. 키가 같은 행은 파일 안에서도 한 번만 추가한다.
5. 변경된 분류·메모만 다른 행은 키가 같으면 기존 행을 유지한다. 기존 거래 정정은 이 MVP 가져오기 동작이 아니다.
6. 기존 DB와의 중복 여부를 미리 표시하기 위해 브라우저는 내용이 아닌 정규화 fingerprint 목록만 FastAPI의 확인 endpoint에 보낸다. fingerprint도 민감 파생정보로 취급하고 요청·응답 로그에서 제외한다. 거래 원문·금액·설명 등 행 데이터는 사용자가 신규 행을 확인하고 승인한 뒤에만 전송한다. FastAPI는 승인된 행에서 fingerprint를 다시 계산해 클라이언트와 같은지 확인한다.
7. API는 승인된 배치를 한 트랜잭션으로 저장하고 unique 제약/충돌 처리를 통해 재요청도 중복을 만들지 않는다. 실패하면 전체 배치를 롤백한다.
8. 결과에 추가, 기존 중복 건너뜀, 파일 내부 중복, 오류·미분류 수를 따로 표시한다. 로그에는 거래값을 기록하지 않는다.

## 분류와 집계 규칙

- 원본 `타입`, `대분류`, `소분류` 텍스트를 별도 보존한다. `타입` 값은 수익, 지출, 이체, 환불 등 집계상 성격으로 명시적으로 매핑한다. 사용자가 만든 원본 타입 매핑은 저장해 다음 가져오기에도 재사용하며 설정에서 수정할 수 있다. 인식하지 못한 타입은 사용자가 정하기 전까지 미분류로 두고 수익·지출 합계에서 제외한다.
- 대·소분류별 합계와 거래 목록을 조회할 수 있다. 수익/지출의 큰 구분과 원본 카테고리는 별도 축으로 유지해 `임대수익` 같은 수익 분류와 `식비`, `보험`, `저축` 같은 지출 분류를 구분할 수 있다.
- 계좌 간 이체는 수익과 지출에서 제외한다.
- 실제 카드 구매는 지출과 카드별 사용액에 포함한다. `대분류`가 `카드대금`인 결제대금 정산 출금은 구매의 중복 정산이므로 일반 지출 및 카드 사용액에서 제외한다. 원본 행과 카테고리 텍스트는 보존한다.
- 환불·취소는 원본 타입/분류에서 의미가 분명하거나 사용자가 환불로 지정한 경우에만 환불로 취급한다. 환불은 수익으로 계산하지 않고 순 지출과 순 카드 사용액에서 차감하며, 합계에서 차감된 환불액도 별도 표시한다. 의미가 모호한 행은 미분류 검토 대상으로 둔다.
- 금액은 부동소수점이 아닌 고정 소수 정밀도로 처리한다. 통화별로 그룹을 나누고 환산하지 않는다.
- 기간은 사용자 로컬 달력 날짜 기준으로 양 끝 날짜를 포함한다. 전체 전월과 전월 같은 날짜까지 비교 기준을 제공한다. 기간 비교는 동일한 일수의 바로 앞 기간으로 비교한다.

## 화면과 사용성

- 승인된 목업 `mockup.html`을 시각 방향 기준으로 삼는다: 단테랩스 크림·네이비 기반, 대시보드에서 수익·지출·차액, 월별 흐름, 분류별 지출과 최근 가져오기 결과를 우선 보여준다.
- 모바일에서는 핵심 지표와 분류 합계를 읽기 쉬운 카드/목록으로 재배치한다. 화면 축소형 데스크톱 표에 의존하지 않는다.
- 가져오기 화면은 파일·시트, 신규/중복/오류 수, 중복 규칙, 거래 미리보기, 명시적 승인 버튼을 제공한다. 모바일에서도 행을 확인하고 승인할 수 있다.
- 로딩, 빈 데이터, 지원하지 않는 파일, 유효성 오류, 저장 성공·실패를 분명히 구분한다. 터치 영역과 키보드 접근성을 갖춘다.

## 시스템 구성과 데이터 경계

- Frontend: Vite + TypeScript 기반 반응형 단일 페이지 앱. 기술 구조상 필요하면 React를 사용하되 기존 lockfile이 있으면 이를 따른다.
- Backend: FastAPI가 같은 출처에서 정적 빌드 결과와 JSON API를 제공한다.
- Database: 개인 서버의 PostgreSQL. 마이그레이션으로 스키마를 관리한다. 브라우저는 DB에 직접 접속하지 않는다.
- 파일 파싱은 브라우저에서 수행한다. 승인 전에는 중복 확인용 fingerprint만 앱 API로 보내고, 승인 후에만 정규화 신규 행을 JSON으로 전송한다. 거래 원문을 외부 API, 분석 도구, CDN, 텔레메트리로 보내지 않는다.
- 권장 단일 사용자 모델은 개인 서버 환경에 주입한 비밀값으로 보호되는 앱 접근 제어다. 브라우저와 앱 서버 구간은 HTTPS로 보호하고 배포는 사설 LAN에 한정한다. 기존 사설 TLS 프록시가 있으면 사용하고, 없으면 공개 인증기관/인터넷 노출 없이 LAN 전용 인증서를 제공하는 프록시 구성을 사용한다. 라우터 포트 포워딩이나 공개 터널을 만들지 않는다.
- DB에는 정규화 거래, import batch 요약, 거래 타입·결제수단 매핑을 저장한다. 원본 파일 전체, 시트 전체, 가져오지 않는 시트, 인증 비밀, 암호화 백업 암호는 저장하지 않는다.
- 제안 엔티티: `transactions`(날짜/시간, 원본 타입·분류, 내용, 고정소수 금액, 통화, 결제수단, 메모, 집계용 분류, 중복 fingerprint, 생성 시각), `import_batches`(시각과 건수 요약), `transaction_type_mappings`(원본 타입과 명시적 집계 방향), `payment_method_mappings`(원본 결제수단 라벨과 `credit`/`debit`/`other`). 정확한 제약과 마이그레이션은 계획에서 구체화한다.

## 개인정보·백업·안전

- 실제 거래값, 설명, 카드명, 고객정보를 코드 fixture, 목업, 문서, 테스트 로그, 오류 추적 도구, 커밋에 넣지 않는다. 테스트와 화면 예시는 합성 값만 쓴다.
- 저장소 루트의 `data/`는 실제 금융 자료 보관 폴더로 간주하고 `.gitignore`에서 제외한다. 사용자의 실제 엑셀 파일을 Git에 추가하지 않는다.
- 요청/오류 로그에는 body와 거래 필드를 남기지 않는다. 애플리케이션이 업로드 파일을 받는 endpoint를 만들지 않는다.
- 인증 비밀, DB 비밀번호, 백업 암호는 저장소 밖에서 주입한다.
- 암호화 백업 파일은 버전 정보, salt, nonce, authenticated ciphertext를 가진다. 복원 전에 복호화·스키마 검증하고, 기존 데이터를 유지하면서 같은 중복 규칙으로 신규 행만 병합한다. 복원 예정 건수를 보여주고 사용자가 승인한 후 원자적으로 반영한다. 잘못된 암호나 손상 파일은 기존 데이터를 건드리지 않는다.
- 웹앱이 집 서버 PostgreSQL에 저장되므로 “브라우저 기기 안에만 저장”이라고 안내하지 않는다. 데이터가 저장되는 위치와 LAN 접근 범위를 사용자 문서에 정확히 표시한다.

## 검증 원칙

- 날짜 파싱·경계, 금액 정밀도, 중복 키 정규화와 재요청, 새 행만 원자적으로 저장, 미분류/이체/카드대금 제외, 환불 차감, 분류별 집계, 백업 복원 실패를 합성 데이터로 검증한다.
- 브라우저 가져오기 파서는 파일 형식/누락 헤더/잘못된 날짜·금액/빈 행/시트 선택 및 외부 요청 없음이 확인되어야 한다.
- API와 PostgreSQL 검증은 전용 테스트 DB에서만 실행하며 운영·공유 데이터를 초기화하지 않는다.
- 모바일 좁은 폭에서 현황 조회·기간 선택·미리보기·승인이 가로 스크롤 없이 가능한지 확인한다.
- 완료 보고는 변경, 검증, 미실행 검사와 사유, 남은 위험을 분리한다.

## 결정 사항과 구현 단계에서 정할 항목

### 사용자와 합의된 사항

- PostgreSQL, FastAPI, Vite + TypeScript.
- 집 안 개인 서버 자체 호스팅, 모바일은 같은 네트워크에서 웹앱으로 조회.
- 주 입력 시트는 `가계부 내역`; 거래 시트가 아닌 `뱅샐현황` 값은 가져오지 않음.
- 동일 거래 판정은 날짜·시간·타입·금액·화폐·결제수단·내용 조합. 일치하면 건너뛰고 기존 행은 가져오기로 수정하지 않음.
- 원본 타입의 사용자 매핑은 다음 가져오기에서 재사용.
- 원본 결제수단의 신용·체크·기타 매핑은 사용자가 지정하고 다음 조회·가져오기에도 재사용. 라벨만으로 추측하지 않음.
- 백업 복원은 기존 데이터에 신규 행만 병합하며 기존 행은 덮어쓰거나 삭제하지 않음.
- 환불이 원본에 명시되었거나 사용자가 지정한 경우 순 지출·카드 사용액에서 차감하고 환불액을 별도 표시. 모호한 행은 자동 판정하지 않음.
- 미리보기에서 확인·승인한 신규 거래만 누적 추가.
- 월별/기간별 수익·지출·차액, 카드별 사용액, 대·소분류별 합계, 모바일 반응형 화면.
- 승인 목업 `mockup.html`의 시각 방향.

### 구현 계획 전 기술 조사로 확정할 사항

- 저장소에 git metadata, 실행 코드, 의존성 manifest/lockfile이 현재 없으므로 scaffold, Python·Node 버전, 패키지 관리자, 라이브러리 버전을 계획 작성 시 설치 환경과 기존 서버를 확인해 선택한다.
- 홈서버의 현재 컨테이너/프로세스 구성, LAN 주소/포트, 방화벽과 TLS 종단, 인증 자격 증명 전달 방식은 사용자의 배포 환경을 조사한 뒤 구현 계획에 기록한다. 앱을 공개 인터넷에 노출하지 않는다.
- 엑셀 파일의 `타입` 값과 날짜·금액 표기 변형은 개인정보를 출력하지 않는 로컬 구조 점검 및 합성 fixture로 확인하고, 알 수 없는 값은 사용자가 매핑한다.
- 계좌 간 이체 및 카드대금 행 식별은 명시적 타입 매핑과 `대분류` 규칙으로 구현한다. 데이터 의미가 정해지지 않은 새 타입은 자동 포함하지 않는다.
- 사용자 정의 기간 집계에서 비교 기간을 직전 동일 일수로 제공하는 것은 설계 기본안이다.
- 배포 계획은 홈서버의 기존 사설 TLS 프록시를 확인하고, 없을 때 LAN 전용 TLS 프록시와 인증서 신뢰 설정을 구성한다. 기본 보안 경계는 사설 LAN 한정, HTTPS, 단일 사용자 인증이며 공개 인터넷 노출은 하지 않는다.
